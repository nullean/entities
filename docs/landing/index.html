Why a record is not enough, in five steps

01 · a record

Types say what a thing is.

Fields and cases. A record describes shape and stops there.

Not enough.

02 · a table

Project it to a schema.

Columns, keys, relations. The database now knows the shape too.

Still not enough.

03 · time

Then time walks in.

Ordering, repetition, drift, deadlines. Those rules live in people's heads and get rewritten a little differently each time.

Nothing says what it must do.

04 · rules

Name the rules, once.

Each rule is a Constraint<Order> next to the type: a name, a sentence, a promise about behaviour. Write constraints, get AutoTests. Code your AI can generate and you can read.

Now the model says what it must do.

05 · guardrails

Nine questions, asked of every rule.

AI writes code faster than you can review it. The constraint metadata generates into CsCheck, which asks each rule nine questions that almost no test suite asks.

You did not read the diff. The rule did.

the rules, written once

Write the rules. Run one line. Plant a bug.

Five named rules and a single test line. Plant a bug and read what the generated test says.

OrderConstraints.csthe rules, written once
[Constraints]
public static partial class OrderConstraints
{
    public static readonly Constraint<Order> TotalNeverNegative =
        Constraints<Order>.Always(o => o.Total >= 0, "An order total is never negative.");

    public static readonly Constraint<Order> ConfirmedOrdersHaveLines = Constraints<Order>
        .When(o => o.Status == OrderStatus.Confirmed)
        .Requires(o => o.Lines.Count > 0, "A confirmed order has at least one line.");

    public static readonly Constraint<Order> LegalMoves = Constraints<Order>
        .Transitions(o => o.Status)
        .Allow(OrderStatus.Pending, OrderStatus.Confirmed)
        .Allow(OrderStatus.Confirmed, OrderStatus.Shipped)
        .Allow(OrderStatus.Pending, OrderStatus.Cancelled)
        .Allow(OrderStatus.Confirmed, OrderStatus.Cancelled);

    public static readonly Constraint<Order> CancelIsRepeatable =
        Constraints<Order>.Idempotent(o => o.Cancel());

    public static readonly Constraint<Order> VersionNeverGoesBack =
        Constraints<Order>.Monotonic(o => o.Version, MonotonicDirection.NonDecreasing);
}

the differentiator

Nine questions almost no test suite asks.

Most tests check whether one example works. The generated tests ask these nine, and each one catches a specific kind of real production bug. Hover, focus or tap a row to watch the bug happen.

The nine questions and the bug each catches
#Test axisQuestionThe bug it catchesAnimation
1Invariant an operation that lets a bad value in
2Idempotency a retry that changes state twice
3Monotonicity an older result overwriting a newer one
4Conservation totals that drift
5Absence a cancelled order that still ships
6Temporal a promise missed by one unlucky gap
7Liveness the endless spinner
8Confluence two rebuilds publishing different results
9Vacancy a green test that checked nothing

when it breaks

A failure you can read. So can your AI.

Each failure names the rule, the operation and the starting value, states the law that was broken and what it costs in production, and arrives shrunk to the smallest case with a seed that replays it (shrinking and seeds come from CsCheck). Rich enough for an agent to read, fix the code and replay.

gradual adoption

      
Start as a warning. Become an error on a date you choose.

      
Nothing breaks on the day you add a rule. Findings are reported until the date you set, and from then on they are errors.
